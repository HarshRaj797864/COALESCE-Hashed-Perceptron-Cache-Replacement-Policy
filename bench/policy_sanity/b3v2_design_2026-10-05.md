# B3 v2 — a sharer directory, and the comparison it must pass (pre-registered)

**2026-10-05.** Written **before** the directory is built or run. The owner
approved the fix on 2026-10-05 (PLAN § 0, "Coherence engine", revised).

## Why

B3 v1 (`b3_ocean4_2026-10-05.md`): on ocean 4c at 2 MB, ChampSim's
store-time sharing rate was 22× below gem5's (R = 0.045). The traffic agreed
(0.89×) and so did the store misses (1.07×). The cause is measured: sharers
are recorded only on LLC lines, and the non-inclusive LLC forgets them when
it evicts the line, which at 2 MB covers 99% of store misses. gem5's L2 is
inclusive and always knows.

## What is built

A **sharer directory**, one per simulation, keyed by physical line address,
independent of LLC residency. It changes no simulated behaviour: it only
records and counts, so every existing statistic must stay bit-identical.

**Presence.** For each line, which of each core's private data caches
(`cpu<N>_L1I`, `cpu<N>_L1D`, `cpu<N>_L2C`) hold it, one bit each.
- A bit is set when that cache **fills** the line.
- It is cleared when that cache **evicts** the line (the victim overwritten
  in `handle_fill`) or invalidates it (`invalidate_entry`).
- TLBs are not data caches and are not tracked.

**Protocol view.** For each line, the set of cores a MESI directory would
list, driven by the requests that reach the LLC:
- a read from core c (LOAD, PREFETCH, TRANSLATION) adds c;
- a store miss from c (RFO) leaves c as the sole owner;
- a writeback from c (WRITE) removes c.

Each request is counted **once**: on an LLC hit in the hit branch, on a miss
where `handle_miss` / `handle_write` accept it. A miss retried because the
MSHR is full is not counted again; the existing hit check *does* run again
on retry, and that is why the hooks are not there.

**Two new LLC counters**, both store-time, per event, read at each RFO
before the protocol view is updated:
- **(a) presence:** the RFO finds another core's private cache holding the
  line;
- **(b) protocol:** the protocol view lists another core.

Plus the number of other cores in each case, and the v1 LLC-mask counter,
unchanged, for continuity.

**A self-check, printed per private cache at the end of the run.**
- The number of mismatches between that cache's valid blocks and the
  directory's presence bits for it. **It must be 0.**
- The number of private caches registered with the directory. **It must be
  3 × cores.**

## Why two counters, and which way each should miss

ChampSim never invalidates a private copy: a store by core B leaves core A's
copy in place.

- **(a) presence overcounts** against a real protocol. A's stale copy still
  "holds" the line, where MESI would have invalidated it, unless A had since
  re-read it.
- **(b) protocol undercounts.** When A re-reads, it hits its stale private
  copy and never reaches the LLC, so it never re-registers. In gem5 that
  re-read misses and A is listed again.

**Predicted bracket:** R_b ≤ 1 ≤ R_a, where R = ChampSim rate / gem5
`(SS+MT).L1_GETX` rate over the same window. Six differences remain from v1:
thread timing, binaries, core model, tree pseudo-LRU, and the two above. So
the bracket is a prediction, not a certainty.

## Pre-registered criteria

The window and gem5 runs are as in `b3_design_2026-10-04.md`: instructions
50 M–150 M, gem5 stopped at 50 M and 150 M and subtracted.

- **Primary: R_b, the protocol view.** It reproduces the mechanism gem5
  counts. **Agreement: 0.5 ≤ R_b ≤ 2 at each LLC size and workload
  compared.**
- **Secondary, a directional prediction: R_b ≤ 1 ≤ R_a.** Reported whether
  or not it holds.
- **Workloads:** ocean 4c at 2 MB and 8 MB; barnes 4c at 2 MB once its gem5
  runs exist. Each is scored separately; no pooling.
- **The checks that qualify any verdict:**
  - the self-check reads 0 mismatches and 3 × cores registered;
  - every pre-existing statistic is bit-identical to the v1 binary, on LRU
    (the comparison runs' rows, all 15 columns);
  - the private regime reads exactly 0 for (a) and (b).
- **Nothing is tuned after R is seen.** A v3 would be a new pre-registered
  comparison.

## Addendum, same day, before any real result: the bracket is weaker than stated

The mechanics test (`5ac2844`'s five cases, all four cores running
`canneal_big0`, which manufactures sharing; 1M+2M) gave presence 24,717 events
and protocol 35,372. **The protocol count exceeds presence.** A third effect is
at work: a core that drops a clean copy silently stays in the protocol view,
as in gem5's sticky lists, but leaves presence at once.

So presence is not a strict upper bound, and **R_b ≤ 1 ≤ R_a may fail** even if
both counters behave as designed. The directional prediction stands as
registered and will be scored; this note records that it is weaker than the
text above argued. **The primary criterion (0.5 ≤ R_b ≤ 2) is unchanged.**
