# B3 — the ChampSim-vs-gem5 comparison, designed and pre-registered

**2026-10-04.** Written and committed **before** either side's numbers exist:
- the ChampSim B3 runs (`b3_ocean4`, `b3_ocean4_scaled`) are still running,
  and nothing has been pulled from them;
- the windowed gem5 runs (`launch_b3_gem5.sh`) have not been launched.

The question: **does the overlay's sharing match what a real coherence
protocol measures on the same program?** This is the validation behind
"the tool is the contribution".

## What is compared

| | ChampSim | gem5 |
|---|---|---|
| program | ocean `-n514 -p4`, traced with Pin from the dynamic SPLASH-3 build (`ocean_4t`, threads 0–3, first 200 M instructions each) | ocean `-n514 -p4`, the static build (`build_splash_static.sh`, `-O2`), whole program ≈ 345 M per thread |
| caches | L1D 32 KB, L2C 512 KB private; LLC 2 MB (`b3_ocean4`) or 8 MB (`b3_ocean4_scaled`), 16-way | MESI_Three_Level: L0 32 KB split, L1 512 KB private, L2 2 MB or 8 MB, 16-way, one bank |
| core | out-of-order, trace-driven | TimingSimpleCPU, execution-driven |
| coherence | shared-VMEM overlay; MESI state + sharer mask at the LLC only | full MESI directory, all levels; FIFO false-alarm check off (`setup_gem5.sh patch-fifo`), randomization off |
| replacement | LRU at the LLC | tree pseudo-LRU (`TreePLRURP`) at every Ruby level, gem5's default; read from the run's `config.ini` |

**The primary metric pair.** Both count store-time sharing events per 1,000
instructions, per event:
- **ChampSim:** `LLC COHERENCE RFO-HIT OTHER-SHARER EVENTS` (`5ac2844`): a
  store that missed the private hierarchy hits an LLC line whose sharer mask
  names other cores.
- **gem5:** L2 `SS.L1_GETX + MT.L1_GETX`: a store miss reaching the shared
  cache for a line other private caches hold
  (`phaseB_metric_semantics_2026-09-23.md`, `gem5_stats.sh`).

**Reported alongside, not part of the criterion:**
- gem5's `SS.L1_UPGRADE` per KI, a store to a line the core already shares,
  which ChampSim cannot see (55–73% of gem5's store-time events so far);
- the writeback-time ChampSim counters, for contrast;
- shared-cache traffic as a check that the hierarchies line up: demand
  accesses per KI and hit rate. On ChampSim's side that is LLC
  LOAD + RFO + TRANSLATION accesses; WRITE is the L2's writebacks, not
  demand. On gem5's side it is `l2_cntrl0.L2cache.m_demand_accesses / hits`.

## The window

ChampSim resets its counters when measurement starts (`CACHE::begin_phase`),
so its numbers cover each thread's instructions ~50 M to ≥150 M.

gem5 with randomization off is deterministic, so a run stopped when any
thread reaches 50 M and one stopped at 150 M share their first 50 M.
`gem5_stats.sh window` subtracts the two, and adds the whole-program run as
a third stop. That gives **three spans: 0–50 M, 50–150 M, 150 M–end**. The
50–150 M span is the one compared.

**The windows still differ in one structural way.** gem5 starts the worker
threads when the main thread spawns them. ChampSim replays every thread from
its own beginning, all at once. The three spans measure whether that
matters: a steady rate across them means alignment is immaterial.

## Known differences, and which way each should push ChampSim

1. **Non-inclusive LLC → undercount.** An RFO that misses ChampSim's LLC finds
   no sharer record, though other cores may hold the line privately. gem5's
   L2 is inclusive and always knows.
2. **Sticky sharer masks → overcount.** ChampSim never back-invalidates, and
   an RFO hit adds the storer without clearing the others. A mask shrinks
   only at a writeback hit, so later stores keep seeing "other sharers"
   that a real protocol would already have invalidated.
3. **Thread timing.** Simultaneous replay versus real spawn and
   synchronization changes the interleavings. Direction unknown.
4. **Binaries.** Dynamic (traced) against static (gem5) builds of the same
   source and input give slightly different instruction streams. Direction
   unknown, expected small.
5. **Core model.** Out-of-order against in-order changes the interleaving
   timing. Rates per instruction should be less sensitive than counts.
6. **Replacement.** LRU against tree pseudo-LRU. These are close, but they
   pick different victims, and a line kept longer is more likely to be found
   shared. Direction unknown, expected small.

## Pre-registered criteria

Let **R = ChampSim rate / gem5 rate** for the primary pair, over the 50–150 M
span, at each LLC size.

- **Agreement: 0.5 ≤ R ≤ 2 at both LLC sizes.** The overlay then reproduces
  a real protocol's store-time sharing rate within a factor of two on the
  same program and window.
- **Disagreement: R outside that band at either size.** It is reported, with
  the decomposition above, as a measured limitation of the tool. Per PLAN
  § 4, not running the comparison is the only fatal outcome.
- **Window check:** if gem5's primary rate varies more than 2× across its
  three spans, the comparison is reported per span with that caveat, and
  the agreement verdict is stated as window-dependent.
- **Hierarchy check:** if the shared-cache demand accesses per KI differ by
  more than 2× between the two, R's interpretation is weakened and the
  verdict says so.
- **Neither side is tuned after R is seen.** No change to the counter, the
  configs or the window choice. A later fix, if one is warranted, is a new
  pre-registered comparison.

## Scope, and what this does not establish

- **One workload, one core count.** Ocean shares little (23× less than
  canneal), which makes the counts small. A second, sharing-heavy workload
  in both simulators is still needed (PLAN § 4): canneal under gem5 SE mode
  is known to be slow, and barnes under gem5 waits on its fortify rebuild.
- **The sharing-degree distribution** is not compared: gem5's
  MESI_Three_Level exports no equivalent.
