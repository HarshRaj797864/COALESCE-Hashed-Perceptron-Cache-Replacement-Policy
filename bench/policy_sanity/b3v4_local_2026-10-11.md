# B3 v4 — what was built and what was checked before the server runs

**2026-10-11.** The design and its predictions are in
`b3v4_coherent_private_design_2026-10-11.md` (`1408479`), committed before
any of this. The simulator change is `2fedebc`. **Nothing here is a result
against gem5.** Those come from the server runs.

## What changed in the simulator

One run setting, `private_coherence`, default 0:

| level | what it adds |
|---|---|
| 0 | nothing: the step-1 simulator |
| 1 (step 2) | an RFO accepted at the shared cache invalidates every other core's private copies of the line |
| 2 (step 3) | level 1, plus the upgrade: a store or RFO that hits a private copy takes the line when the directory lists another core |

At levels 1 and 2, a fill that reaches a core after another core has taken
the line completes its instruction and leaves no copy.

Every log now prints `PRIVATE-CACHE COHERENCE LEVEL: N`. A binary older than
this ignores the config key and prints nothing, so a missing line means the
run was at level 0 on an old binary. `run_phase_a.sh` refuses to launch such
a binary with a level set, and the rows carry the level each run printed.

## Checks, all on the laptop

**1. Exact counts: 27 of 27 runs match the pre-registered hand counts.**
`check_coherence_exact.sh`, eight cases at three levels, plus `order` in the
private regime. The numbers were committed before the code existed, and the
first build hit all of them.

| case | level 0 | level 1 | level 2 |
|---|---|---|---|
| `pingpong`, events per 50 rounds | 50 | **150** | 150 |
| `order`, cores found present | 200 | 150 | 150 |
| `upgrade`, upgrade events | 0 | 0 | **100** |
| `upgrade_l2`, upgrade events, all seen in an L2C | 0 | 0 | 50 |
| `storm`, stale fills dropped | 0 | 450 | 450 |

Every run reads self-check 0, 12 caches registered and stale-holder check 0.

**2. Level 0 is the previous simulator.** On real traces (canneal and barnes,
4 cores, shared, 2 M + 10 M instructions), the new binary at level 0 and the
previous binary (`e5f5a66`) produce logs with **no existing line changed**:
0 lines removed, 301 added, all of them the new counters (reading 0) and the
level.

**3. The three build guards pass.**

**4. The rule that starts the A5 rerun is tested by injection.**
`test_b3_gate.sh` feeds `b3_score.py gate` a correct set of rows and 17
faulty ones. It passes the correct set and refuses each fault for the stated
reason: wrong level, a row from an old binary, a missing row, an incomplete
run, a wrapped trace, a self-check or stale-holder count, a moved private
row, a counter firing at level 0, canneal or ocean out of the band.

**5. The published numbers are unchanged by the scorer's changes.**
`b3_score.py score … v2 v3` and `same … v2 v3` give byte-identical output
before and after.

**6. The launch was rehearsed end to end** against a copy of the server's
layout, with 1 M-instruction runs. See below.

## The rehearsal

A scratch home directory laid out as the server's, the real canneal and
barnes traces, stand-in ocean traces, and 0.2 M + 0.8 M instructions per run.

**The launch, `launch_b3_v4.sh`:**
- `plan`: 12 queues, 2 jobs each, nothing unrunnable. With the previous
  binary in place it refuses: "bin/champsim predates B3 v4".
- `go`: the exact counts pass on the binary; it is kept under a name carrying
  its md5; the 12 queues start on that copy; the chain starts.

**The chain, `b3v4_chain.sh`, on those 24 runs:**
- **Q0 held:** the 4 level-0 control rows equal their step-1 rows, which a
  separate launch had made on the previous binary.
- **Q1 held:** the 5 private-regime rows at level 1 and the 5 at level 2
  equal their step-1 rows.
- **Q2 held:** every row complete, self-check 0, 12 registered, stale-holder
  check 0, the level asked for.
- **R_b means nothing at this length** (0.8 M instructions against gem5's
  50–150 M window, and stand-in ocean traces). Two values fell outside the
  band, so the chain wrote "RULE NOT MET" and started nothing. That is the
  refusing path, working.
- **The starting path**, with a stand-in gate that says PASS: the chain
  started both rerun queues with `--private-coherence 2` (and
  `--llc-per-core-mb 2` for the scaled one), the nine policies, longest
  first, on the frozen binary, and installed both reboot entries.

**The rerun queues it started ran to the end:** 40 runs, the nine policies
on canneal and the stand-in ocean at 4 cores, both geometries (the 8- and
16-core jobs were skipped: the laptop has no such traces). Every row printed
level 2, completed, and read self-check 0, 12 registered and stale-holder
check 0. The 4 private-regime rows read 0 invalidations and 0 upgrades.

**It found one defect in the new scripts**, fixed before the real launch: the
chain's preflight piped `b3_score.py`'s usage text into `grep -q`. The usage
exits 2, so under `pipefail` the check failed with the text present. This is
the same trap as `1a2b8ca`.

## Not checked here

- **Full-length behaviour.** The longest local real-trace run is 12 M
  instructions per core. The server runs are 150 M.
- **8 and 16 cores on real traces.** The laptop has only the 4-thread
  traces. The A5 rerun queues LRU in the private regime at 8 and 16 cores,
  which measures there what Q1 asserts.
  - What was run instead is a **16-core stress test, never a result**: the
    four canneal threads given to 16 cores four times over, which
    manufactures contention, at level 2 under LRU and COALESCE, 1 M
    instructions a core. Both runs completed with 48 caches registered,
    self-check 0 and stale-holder check 0, through 1.17 M invalidations,
    63 thousand upgrades and 639 thousand dropped fills.
- **The server's compiler.** `launch_b3_v4.sh go` therefore runs the fast
  exact cases on the server's own binary first, and launches nothing if one
  count is off.
